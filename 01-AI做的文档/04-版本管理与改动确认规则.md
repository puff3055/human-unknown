# HUMAN UNKNOWN 版本管理与改动确认规则

日期：2026-09-05

## 一、GitHub 仓库

- 仓库：puff3055/human-unknown
- 可见性：Private
- 主分支：main
- 当前基线：v0.1.0-particle-baseline
- 基线含义：保留纯粒子首页、凝视交互、靠近状态以及此前全部参考材料和方案文档。

## 二、最高优先级规则

从现在起，任何会改变页面视觉、交互、文案、结构或代码逻辑的工作，都必须遵循：

> 先提出方案 → 等待用户确认 → 创建独立改动分支 → 修改代码 → 浏览器验收 → 保存版本。

用户没有确认方案前，不修改代码。

用户只是提出意见时，先复述我对问题的理解，并给出产品方案、视觉方案、交互规则、影响范围和验收标准，不把意见自动视为实施授权。

## 三、每次改动的标准流程

### 1. 保存改动前状态

- 检查工作区是否干净；
- 确认当前 main 已经推送到 GitHub；
- 对需要长期保留的稳定状态建立版本标签。

### 2. 只提交方案

- 方案文档放入 01-AI做的文档；
- 明确写出为什么改、改什么、不改什么、技术方向和验收标准；
- 把方案发给用户确认；
- 此时不动 02-代码仓库中的页面代码。

### 3. 用户确认后再建立分支

分支按目的命名，例如：

- feature/texture-field
- feature/idle-breathing
- fix/gaze-latency

每一个分支只解决一个已经确认的问题，避免多个方向混在一次修改里。

### 4. 实现与验收

- 修改只发生在独立分支；
- 保留参考图与实现截图的同屏对照；
- 验证静止、鼠标移动、靠近、移动端与性能；
- 没有达到方案里的验收条件，不合并到 main。

### 5. 保存可回滚版本

通过验收后：

- 提交本次实现；
- 推送分支；
- 合并到 main；
- 建立清晰的版本标签；
- 在交付说明中写明版本名称、主要变化和回滚点。

## 四、版本命名

- v0.1.0-particle-baseline：当前纯粒子基线。
- v0.2.0-texture-field：未来经确认并完成的纹理场版本。
- v0.3.0-idle-breathing：未来经确认并完成的无交互呼吸版本。
- 小范围参数微调使用补丁号，例如 v0.2.1。
- 尚未得到最终确认的候选版本使用 rc，例如 v0.2.0-rc.1。

具体版本顺序可以随实际决策调整，但已经发布的标签不覆盖、不改名、不删除。

## 五、回滚原则

- 优先从版本标签建立恢复分支，不破坏历史记录；
- 已经推送到 GitHub 的版本不使用强制推送覆盖；
- 需要撤销某次修改时，使用新的回滚提交，而不是删除旧提交；
- 回滚前先向用户说明将恢复到哪个版本、会失去哪些后续变化；
- 当前基线可以随时恢复到 v0.1.0-particle-baseline。

## 六、每次方案必须回答的问题

1. 用户现在看到的问题到底是什么？
2. 这个问题为什么会发生？
3. 下一版要制造什么具体感受？
4. 哪些视觉和交互保持不变？
5. 计划采用什么结构实现？
6. 有什么风险和取舍？
7. 如何判断它真的改对了？
8. 用户确认后才进入哪一部分代码？
